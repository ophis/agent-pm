# CLAUDE.md

Unattended agent pipeline driven by a Linear board: launchd-scheduled Python scripts pick Todo issues assigned to a role account (any project; the project is the product, the assignee is the stage: researcher → pm → engineer) and start one `claude -p` run per issue; each run is that role (`roles/<role>.md`) doing one of its tasks (`tasks/<task>.md`): the one the issue's `Tasks` label picks by id through `pipeline.toml`'s `[task_labels]`, else the role's default (first in `tasks`).

## Commands

```bash
python3 -m unittest discover -s scripts/tests            # all tests; no network, Keychain or Claude
python3 -m unittest discover -s scripts/tests -k attempt # tests whose name matches
python3 scripts/router.py --now --dry-run                # one tick: plan + usage probe, changes nothing
python3 scripts/promote.py --dry-run                     # what Handoff and prune would do
tmux ls                                                  # running sessions, agent-pm-<role>
tmux attach -t agent-pm-<role>                           # watch a role's live run
```

Python 3.11+ (`tomllib`); launchd uses `/opt/homebrew/bin/python3` because macOS `/usr/bin/python3` is 3.9. Without `--dry-run`, a router tick or `--pick` claims a real issue and starts claude, and promote mutates Linear.

## Architecture

- `scripts/router.py` (every 30 min, all day: the plist passes `--now`): per-role tmux locks (`tmux has-session -t =agent-pm-<role>`, `=` for an exact match; all busy → skip before any Linear query) → Recover (resume or requeue dead In Progress runs) → usage gate → resume or claim → `launch.py`, at most one launch per tick. Recover and claim see only idle roles' issues. Queue and Recover cover the team's issues in a project assigned to a role account (matched by Linear user id); claim and requeue change only the state, so the assignee stays. Order: priority, later role, oldest. Claim takes only ready Todo issues (every direct `blocks` blocker Done/Canceled/Duplicate; archived = done, unreadable = not), read once per run; blocked ones log `blocked: X by Y`, and a tick whose idle roles' Todo is all blocked skips the usage probe. A claim resolves the task from the issue's labels in the pre-claim re-check (`task_for`: the `Tasks`-group label's id → task via `[task_labels]`, the name is ignored; no such label → the role's default; several labels, an id not in `[task_labels]` or a task not the role's → comment, In Review, no run); startup stops when a `[task_labels]` id isn't one of the group's labels (`pipeline.task_group`, one query); `--pick` and `--claim` take only default-task issues.
- `scripts/launch.py` starts `claude -p` in tmux session `agent-pm-<role>` with cwd `work/<ID>/`. The role is the one whose `account` is `--assignee` (case-insensitive), running `--task`, which must be one of the role's `tasks` (else `config-error`, exit 2); the task supplies its file, model, effort, `add_dirs`, `repo_from_issue`, `read_repo`, `allowed_tools` and project log, the role the charter, `read_only`, memory, key and tmux session. It checks the role's Keychain item (`security find-generic-password -s <key>`, no `-w`; missing → `config-error`, exit 2) and exports `LINEAR_KEYCHAIN_SERVICE=<key>`, so the run acts as the role's Linear account; it never reads a key. A `[docs]` clone that is not a directory is also a `config-error` (exit 2). The prompt passes `roles/principles.md`, the charter and the task by absolute path, plus a tail line of ids (`Humans:`, `Project:`, `Team:`, `States:`, `Docs:` for `[docs]`'s repo, clone and branch), `Project repo:` (the project's `[project_repos]` repo or `none`, once) for `read_repo` tasks and runs whose role's `next` runs a `repo_from_issue` task, and, for `repo_from_issue` tasks, `Repo check:` from `eng.resolve`. A `read_repo` task also gets `research.py: python3 <ROOT>/scripts/research.py` after `Docs:`, `AGENT_PM_ISSUE=<ID>` in its env, Edit denies on `work/<ID>/src/**`, `scripts/**` and the mapped project's clone `~/playground/<name>` (`<clone>/**`, or, when the run dir is inside it, each top-level entry but the run dir's, listed at launch), and `--allowedTools` with three exact rules (`Bash(python3 <ROOT>/scripts/research.py prepare)`, and the two halves of deep-research's brake probe, `Bash(<PROBE>)` and `Bash(python3 <ROOT>/scripts/router.py --gate new)`), the only launcher-owned exceptions to the task `allowed_tools` trust model (`pipeline.check_allowed_tools`). After the repo step (so exits 2/3 write nothing) it builds the session record (`sessions.base`: sid, cwd, key's service name, `started_at`). The tmux script: exports, `launch` line → `sessions.py start ISSUE RECORD_JSON` → `claude` tee'd to the project log, `rc=${PIPESTATUS[0]}` → the `end … exit=$rc` line to the project log and `runs.log` → `sessions.py end ISSUE RECORD_JSON "$rc"`. Both registry calls are `shlex.join`ed, log to the project log, and their status is never checked.
- `scripts/sessions.py` (no LLM; imports only `pipeline`): the session registry, one comment per session on its issue. `linear_gql` uses `harness_key`, not the script's `LINEAR_KEYCHAIN_SERVICE`, so `isMe` is the harness account. Each write runs `Q_FIND` (the issue's `isMe` comments whose body starts `Run <sid> · `), then `commentUpdate`s the earliest, else `commentCreate`s; a failed find writes nothing. `body`: `Run <sid> · running · <started_at>` (`start`) or `Run <sid> · <done|interrupted> · <started_at> → <ended_at> · exit <rc>` (`end`; `done` for RC 0), a blank line, then a fenced code block holding only `command(rec)` (`cd <cwd> && LINEAR_KEYCHAIN_SERVICE=<key> claude --resume <sid>`, shell-quoted). A resume (same sid) edits the comment, a new sid adds one. One attempt for both calls in a daemon thread joined for `LIMIT` (10 s), with `linear_gql(timeout=LIMIT)`; any failure (including bad argv) prints one `registry-error` line (type and message only, so no key) and exits 0. Promote leaves `is_comment` comments (`user.isMe` and body starting `Run <SID> · `) out of `## Comments`, and old `Run` attachments (`is_record`: the URL prefix `https://agent-pm.invalid/run/`, not the title) out of `## Source`.
- `scripts/eng.py`: the Engineering repo step (`resolve`: the issue's `Repo:` line, else its project's `[project_repos]` entry; clone into `~/playground/<name>`, pick the `<ID>-<slug>` branch), a `status`/`comments` CLI the Engineering run calls, and the repo utilities `resolve`, `research.py` and `prune.py` share: `read_issue`, `target` (the repo part of `resolve`, returning `Target`; `push=False` skips the push-permission check), `run_subdir` (a run-dir subfolder that must resolve inside the run dir) and `locate` (a linked worktree's clone, branch, HEAD and gitdir, read from files only; `ValueError` if it is not one).
- `scripts/research.py prepare` (called by `read_repo` runs; issue from `AGENT_PM_ISSUE`): `eng.target` with `push=False`, then the detached worktree `<wt>` = `work/<ID>/src/<name>`: `git -C <clone> fetch origin`, then `git -c core.symlinks=false -C <clone> worktree add --detach <wt> origin/<default>`. An existing `<wt>` is reused with no git run (checked from files through `locate`: a worktree of the target clone, detached HEAD); one whose gitdir is `locked` (an interrupted add) is removed and re-added. Prints one JSON line (`repo`, `mapped`, `clone`, `default`, `worktree`, `commit`, `reused`); exit 2 = `Invalid` (the run asks about the target), 1 = any other failure. Its only writes to the clone are `gh repo clone` (missing clone), `fetch`, `worktree add` and `worktree remove`.
- `scripts/promote.py` (every 5 min, no LLM): Handoff issues in a project, assigned to a role account whose `[roles.<role>]` has `next` → a new issue in the same project, assigned to the next role's account; the child id is a hash of source, next role and handoff time, which makes reruns idempotent. Each tick ends with `prune.py` (force-deletes the `work/<ID>/worktrees/*` and `src/*` worktrees of issues finished ≥ 24 h ago; archives the pm and engineer ones).
- `scripts/pipeline.py`: shared Linear GraphQL client (the harness account's key, from the Keychain service `harness_key` in `pipeline.toml`), config loading and validation (`load_config`, `registry`, `runnable`, `role_ids`). Router, launcher and promote run `runnable`; router and promote also `role_ids`, which stops them when a role account is missing in Linear.
- Identity: router, promote, prune and `sessions.py` act as the harness account `frank.agent.w@gmail.com`; each run as its role's `account` (`roles/<role>.toml`). Only Keychain service names travel in env vars, argv, logs and prompts, never keys.
- Every move to In Review, by a run (`roles/principles.md`) or the harness (router's attempt cap, promote's bounce), also subscribes each `human_members` email (`issueSubscribe`) and keeps the assignee.
- State between ticks is only `logs/runs.log` (start/resume/end lines; start and resume end with `task=`, which resume and Recover use, never the labels) plus Linear issue history; the router never reads session records. Resume finds a session at `~/.claude/projects/<escaped work/<ID>>/<sid>.jsonl`, so moving the repo or `work/` orphans resumable sessions.

## Roles, tasks, rules

- Every `roles/<role>` and `tasks/<task>` is an `.md` + `.toml` pair, and every role is runnable: its default task is the first in `tasks`. `pipeline.toml`'s `[roles.<role>]` holds `next` and `require_instructions`. Allowed keys are the `*_KEYS` sets in `pipeline.py`; an unpaired file, an unknown key, a `[task_labels]` key without a task pair or a task with both `read_repo` and `repo_from_issue` stops router, launcher and promote.
- Where a rule goes: holds for every role → `roles/principles.md`; every task of one role → the charter `roles/<role>.md`; a document format → `templates/`; this task only (claiming, failure, hand-off, resume) → `tasks/<task>.md`. One rule, one place. Precedence: principles > charter > task.
- Every task file defines a resume rule; the rules every resume shares are in `roles/principles.md`. A resumed session re-reads all three files.

## Gotchas

- Runs get `--setting-sources user --strict-mcp-config`, so this file and project settings don't load in them. A run reaches only `work/<ID>/` and its `--add-dir`s (`roles/`, `tasks/`, `templates/`, the task's `add_dirs`, the role's `memory`; the docs clone reaches runs through `add_dirs`' `{docs_clone}`); give a task any new path through `add_dirs`, or the run stalls on a permission nobody can grant.
- `test_launch.py` asserts exact prompt strings and `claude` flags; update it with any prompt or flag change.
- Code, config and tasks identify Linear entities (team, states, label groups, labels, projects, users) by id, never by name; names appear only in logs and comments. Exception: a role's `account` is its user's email. Roles are referred to by name.
- `logs/` (gitignored) is runner state: keep it; launchd can't start a job whose log dir is missing.
- Schedules are `scripts/*.plist`, installed as copies in `~/Library/LaunchAgents/` (reload with `launchctl bootout` + `bootstrap`); they hold absolute paths. The router plist passes `--now`, which skips `router.py`'s 01–06 hours check; drop it to run only at night.
- Linear's issue lists can lag a just-made state change; re-read the issue's state before acting on it.
