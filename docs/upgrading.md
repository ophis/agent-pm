# Upgrading

This covers upgrades from v0.6.20 on; upgrades from before v0.6.20 are not covered. Before upgrading, do the
[Upgrading steps](#upgrading-steps) that apply.

## With scripts/install.sh

On a machine already set up, by hand or by [`scripts/install.sh`](../README.md#install), run the same command again, with
`--ref <ref>` for a branch: it reads your answers from its last run, else from `~/.agent-pm/config.local.toml`, else
asks; skips what is installed and logged in; installs what the configuration lacks; and shows and asks before each
change to your config or shell profile. Flags change the configuration (`--clients`, `--docker`/`--no-docker`, the
`--opencode-*` flags); it removes nothing chosen before.

It does not update what is installed, but for OpenCode's agent-pm plugin: when `--ref` (default `main`) names a newer
commit than the one it last downloaded, it deletes OpenCode's copy and downloads it again, and the `~/.agent-pm/bin`
commands run the new copy. Update the other plugins (Claude Code: `claude plugin marketplace update agent-pm`, then
`claude plugin update agent-pm@agent-pm`; Codex: `codex plugin marketplace upgrade agent-pm`), then rerun it: when
the plugin's broker sources changed it reinstalls the broker and asks its logins again ([Log in](docker-host.md#log-in)).
Do the [Upgrading steps](#upgrading-steps) that apply as before: it does not edit config keys a release renames.

## Upgrading steps

Nothing migrates automatically. Do each row that applies, once, by hand or through an agent.

| If you have | Do |
|---|---|
| a Docker Host using an older broker | Reinstall the broker from this checkout ([Install](docker-host.md#install)): protocol 17 adds authenticated OpenCode provider availability checks for the board's usage gate. Python requires an exact protocol match; the provider key stays in the existing broker-only Keychain item. |
| Docker `plugins` entries in the old `name@marketplace` format | Use `autopilot` for the default plugin, or `name@owner/repo` for another public GitHub marketplace. Plugins now install independently inside the image on refresh; host installations no longer supply them. If an older installer wrote `plugins = []` because Claude was absent, remove that override to restore default autopilot; keep an intentional empty list. [Plugins](docker-host.md#plugins). |
| an earlier `scripts/install.sh` run | Reruns keep saved Board and job choices. Select a tracker with `--board local` / `--board linear` (bare `--board` now needs one); router/promote jobs are separately optional. Choices and rerun behavior: [Board setup](board.md#setup). |
| a Docker Host with GitHub (`login github agent-pm-bot` done) | After the broker reinstall, rerun `"$B" login github agent-pm-bot`: the broker now saves the App's slug, and an older `agent-pm-github-users` item is `login_required`. `[session.hosts.docker.github] app` defaults to `""` now: set `app = "<slug>"` (the login prints it; `agent-pm-bot` for that App) in `~/.agent-pm/config.local.toml`, or rerun `scripts/install.sh`, which writes it. Until then Docker sessions get no GitHub token. |
| `~/.agent-pm/config.local.toml` set up for a Linear board | Machines that use Linear must add this line under `[orchestrator]`: `tracker = "linear"` (after the next row, if it applies). `[orchestrator] tracker` picks where issues live, and unset it is `"local"`: the [local board](board.md#local-board) in `$AGENT_PM_BOARD_DIR`, default `~/.agent-pm/board/`, its runtime state in `<board>/.state/` instead of `<work_dir>`. Left out, the launchd router (and `router --dry-run`) exits 2 with `router.py: /Users/<you>/.agent-pm/board: no such board directory`; `promote` and `prune` exit 2 the same way (`promote.py: /Users/<you>/.agent-pm/board: no such board directory`), and `issue` reads the local board, exiting 2 with `agent-pm-orchestrator issue: /Users/<you>/.agent-pm/board: no such board directory`; a board run still running at the upgrade cannot write back (`writeback` exits 2 with `agent-pm-orchestrator writeback: <ID>: session <sid>'s start row key: '<key>'` and logs `writeback refused`): add the line before it does. |
| `[linear_orchestrator]` or `[linear_orchestrator.<table>]`, or Linear keys directly in `[orchestrator]` or `[orchestrator.roles.<role>]`, in `~/.agent-pm/config.local.toml`; board runs still running; the `agent-pm-linear` command in scripts or installed launchd jobs; scripts, `PYTHONPATH` or local plist edits naming `linear-orchestrator/` or `agent_pm.linear_orchestrator` | Do this row first: the rows below name the new sections and command. 1. Before upgrading, let every board run finish, or close it: its Record names `agent-pm-linear`, which no longer exists, so after the upgrade it can be neither resumed nor recovered. 2. Rename each section to `[orchestrator]` or `[orchestrator.<table>]` (e.g. `[orchestrator.core.roles.<role>]`). 3. Move the Linear keys into `[orchestrator.linear]`: `team`, `human_members`, `harness_key`, `task_label_group` and `agent_label_group` from `[orchestrator]`; `[orchestrator.states]`, `[orchestrator.task_labels]`, `[orchestrator.agent_labels]` and `[orchestrator.project_repos]` become `[orchestrator.linear.states]`, `[orchestrator.linear.task_labels]`, `[orchestrator.linear.agent_labels]` and `[orchestrator.linear.project_repos]`; each role's `account` and `key` move from `[orchestrator.roles.<role>]` to `[orchestrator.linear.roles.<role>]`. `work_dir`, `[orchestrator.task_tiers]`, `[orchestrator.client_max_runs]`, `[orchestrator.local_clones]`, `[orchestrator.core]` and the roles' `max_runs` stay; delete `next` and `require_instructions` (the `next` row below). Left there, a flat key stops every command with e.g. `unknown key 'team' in [orchestrator]` or `[roles.<role>] has unknown keys: account, key`, and an old `[linear_orchestrator]` section is ignored, so the command refuses with `required, unset: linear.team, …` (the router logs that one as `config-error`). 4. Replace `agent-pm-linear` with `agent-pm-orchestrator` (`bin/agent-pm-orchestrator`) in scripts and local plist edits, and point paths at `orchestrator/src` and `orchestrator/launchd/`: the project is now `orchestrator/`, its package `agent_pm.orchestrator`, its engine modules `agent_pm.orchestrator.engine.<module>` (Linear bindings — `client`, `ops`, `linear_tracker`, `issue_*` — `agent_pm.orchestrator.trackers.linear.<module>`; the `issue` command `agent_pm.orchestrator.issue.command`; were `agent_pm.linear_orchestrator.engine.<module>`; `flow` is `agent_pm.orchestrator.engine.flow`). 5. Reinstall the launchd jobs ([Board › Setup](board.md#setup) step 4): the installed ones run the removed `bin/agent-pm-linear`. |
| `[orchestrator.linear.states]` in `~/.agent-pm/config.local.toml` without `backlog` | Before upgrading, note the id of the team's Backlog state (`agent-pm-orchestrator issue lookup states`); after it, add `backlog = "<id>"`. Until then every orchestrator command refuses with `required, unset: linear.states.backlog` (the router logs it as `config-error`). A Backlog issue now loses its checkouts and temp files after 7 days like an In Review or Handoff one ([Using the board](board.md#using-the-board) › Finish). |
| scripts, notes or prompts running `agent-pm-orchestrator issue list`, `create` or `move` with Linear values | Use the abstract names: `move <ID> <state>` replaces `move <ID> --state <name>`, a state being `backlog`, `ready`, `running`, `review`, `approved`, `done` or `canceled` (`list`/`create --state` too); `--role <role>`, `--role me` or `--role unassigned` replaces `--assignee`; `--team` is gone from `list` and `create` (the configured team); set an issue's task, client and priority with `--task <name>`, `--client <name>` and `--priority none\|urgent\|high\|medium\|low`, and change them, the title or the description later with `issue edit`. Left as they were, the commands exit 2 with a usage error. `lookup`, `label swap`, `--label`, `--project` and `--milestone` stay, for Linear only. |
| `/agent-pm:linear` in prompts, notes, permission rules or a Codex `AGENTS.md` | Use `/agent-pm:board`: the skill was renamed and `/agent-pm:linear` no longer exists once the installed plugin is updated. |
| the router launchd job with `--now`, or scripts calling `agent-pm-orchestrator router --now` | Drop `--now`: the router now runs whenever started, at any hour, and refuses `--now` with exit 2 (`usage: …`). Reinstall the router job ([Board › Setup](board.md#setup) step 4). An In Progress issue with no run now returns to Todo 2 hours after its latest move into In Progress, not after its latest edit; one with no such move in its history returns at the next tick. |
| `linear.human_members` relied on to decide whose comments count, or other accounts (the manager's) commenting on or moving board issues | Every account but the harness account, the role accounts and Linear automation now counts as the user, so the manager's comments are instructions and its moves to Todo restart the attempt count. The manager's `agent-pm-orchestrator issue` commands now act as a new `linear.manager_key` account instead of the harness: pick an account that is neither the harness nor a role (yours, or one more team member), create its API key, store it ([Linear presets](credentials.md#linear-presets) step 3) and set `manager_key` under `[orchestrator.linear]` in `~/.agent-pm/config.local.toml`; unset, every `issue` command refuses with `linear.manager_key is unset`, and one equal to `linear.harness_key` or a role's key stops every command; comments without a user (the GitHub integration's) are ignored. `linear.human_members` only picks who is subscribed on In Review, and an email in it that is not in Linear no longer stops the router (the failed subscribe shows in the In Review comment). Comment through a role account where a comment must not count, and keep the team's membership and guest access tight, since `human_members` no longer gates this. |
| `next` or `require_instructions` in `[orchestrator.roles.<role>]` in `~/.agent-pm/config.local.toml` | Delete them: the workflow is their only source. To change a stage's `next` or its instructions rule, copy `orchestrator/src/agent_pm/orchestrator/engine/flow/workflow.toml`, edit that stage and set `[orchestrator] workflow` to the copy's path ([On the board](customizing-roles-and-tasks.md#on-the-board)). Left there, every `agent-pm-orchestrator` command stops with `[roles.<role>] has unknown keys: next`. |
| scripts or monitors reading the exit code of `agent-pm-orchestrator router`, `promote` or `prune` | A configuration error, a rejected Linear setup (bad ids, a missing Keychain key) included, now exits 2, not 1; 1 now means Linear was unavailable (and, for `prune` and `router --issue`, an unknown run inventory or a failed step). |
| running agent-pm sessions | Close them first, Docker Host ones before you reinstall the broker too: a reinstalled broker cannot read, so cannot revoke, the old one's GitHub tokens. After a reinstall, delete leftover `agent-pm-tokens` and `agent-pm-revocations` items in Keychain Access (their tokens expire within an hour), then [log in](docker-host.md#log-in) again. |
| `pty` in `~/.agent-pm/config.local.toml` (`[session.hosts] default`, `[delegate.delegates] harness_host`, a `[session.hosts.pty]` table) or in scripts (`--host pty`); pty Host sessions (the pty Host, removed) | Close pty sessions before upgrading: afterwards nothing reaches them. Set `default` and `harness_host` to `tmux` or `docker`, drop `--host pty`, delete `[session.hosts.pty]`, then delete `~/.agent-pm/pty/`. Left there, `default = "pty"` fails with `[hosts] default: 'pty' is not a Host here (removed Hosts: docs/upgrading.md); want one of docker, tmux` (with `[session.hosts.pty]` still there, first with `[hosts.pty].implementation: want module.path:Class` or an import error), `harness_host = "pty"` with `[delegates] harness_host: want one of docker, tmux`, `--host pty` with `--host pty: want one of docker, tmux`. |
| `[orchestrator.selection]` in `~/.agent-pm/config.local.toml` (model selection, removed) | Delete it with its `selector`, `resolvers` and `translate` keys. Left there, `agent-pm-orchestrator` refuses with `unknown key 'selection' in [orchestrator]`; only `writeback` reports and ignores it. |
| `[orchestrator.core.roles.choice-translator]` or `[delegate.roles.choice-translator]` in `~/.agent-pm/config.local.toml` | Delete them: the `choice-translator` role and its `translate` task are gone. Left there, the orchestrator refuses with `unknown role 'choice-translator' in [overlay.roles]` or `roles.choice-translator: no charter roles/choice-translator.md in core or team_dirs`. |
| `[selector]` or `[selector.jev]` in `~/.agent-pm/config.local.toml`, Keychain item `typesafe-jev` | Delete them: nothing reads them any more (the config table is ignored). |
| `runs.jsonl` start rows with `tier` and `effort`, written while `[orchestrator.selection] resolvers` was non-empty | Nothing to do: readers ignore those fields. Resuming such a run uses its task's `[task_tiers]` tier and the role's configured effort, not the recorded choice. |
| board OpenCode runs relying on v0.6.32's packaged `[client_max_runs] opencode = 1` | Add `[orchestrator.client_max_runs]` `opencode = 1` to `~/.agent-pm/config.local.toml`: the packaged config no longer limits any client ([Run limits](board.md#run-limits)). |
| role runs begun on v0.6.30 or earlier | Let them finish first: an outcome's `summary` now holds at most 300 characters (4000 before), so `agent-pm-orchestrator writeback` refuses a longer one with exit 2, and the run's Linear comment waits for Recover. |
| Docker Host workspace volumes `agent-pm-ws-*` whose worker gets `Permission denied` writing its cwd (root-owned roots, v0.6.23 or earlier) | Close the session, then `/usr/local/libexec/agent-pm/agent-pm-broker workspace-rm --volume <volume>` (it holds no work); the next start recreates it agent-owned. |
| `[session.hosts.docker.github] app`, broker protocol 12 or earlier | After upgrading plugin and broker, run `/usr/local/libexec/agent-pm/agent-pm-broker login github agent-pm-bot` once: until it saves the bot user ID, a start fails with `login_required`. |
| `[session.clients.opencode.providers.<name>]` tables and Docker OpenCode, broker protocol 14 or earlier | After upgrading plugin and broker, run `/usr/local/libexec/agent-pm/agent-pm-broker login opencode <name>` for each: until then a Docker OpenCode start fails with `login_required`. |
| Docker Claude, broker protocol 15 or earlier | After upgrading plugin and broker ([Install](docker-host.md#install): reinstall, `sudo` asks once), run `/usr/local/libexec/agent-pm/agent-pm-broker login claude` (and `login claude <name>` for each [registered account](docker-host.md#claude-accounts)), then `security delete-generic-password -s agent-pm-claude -a setup-token ~/Library/Keychains/login.keychain-db`: nothing reads that item any more. Until the login, a Docker Claude start fails with `login_required`. |
| a Docker Host broker installed before the worker image set `core.hooksPath` (`/etc/gitconfig`) | Rerun [Install](docker-host.md#install) (`sudo` asks once) and [log in](docker-host.md#log-in) again; the new broker's changed Dockerfile is a new image key, so the next start rebuilds the image (or `build --agent-pm "$PKG"` now). Until then Docker Host checkouts run no `.githooks/`. |
| Docker Codex installed with broker protocol 11 or earlier | [Upgrade existing installations](docker-codex.md#upgrade-existing-installations). |
| scripts calling `/opt/agent-pm/bin/with-secrets` by hand | Add `--client <client>` (`claude`, `codex` or `opencode`); without it the command refuses. |
| keychain items `agent-pm-engineer` or `agent-pm-docs` (GitHub App private keys) | The broker serves only the App `agent-pm-bot` (App ID 5352992): store its key as [Log in](docker-host.md#log-in) says (service `agent-pm-bot`, account `5352992`), run `/usr/local/libexec/agent-pm/agent-pm-broker login github agent-pm-bot`, and delete the two old items. |
| `mount_roots` in `[session.hosts.docker]` | Delete it (workspaces are [volumes](docker-host.md#workspace-volumes)); left there, the Docker Host refuses it with `unknown key`. |
| `[session.hosts] default = "docker"` with unattended board runs | They now run in containers ([Role runs](docker-host.md#role-runs)): set `[delegate.delegates] harness_host` to another Host and drop host `read`/`write` dirs from their roles. |
| `default_task` or `tasks` in a role table | Drop `default_task`. Move each `<prefix>.roles.<role>.tasks.<task>` table's keys to `<prefix>.roles.<role>`, for the prefixes `delegate`, `delegate.clients.<name>` and `orchestrator.core`. |
| `[session.clients.codex]` `sandbox`, `shell_network` | Express them in `[session.clients.codex.modes]` `auto` ([Client policy](sessions.md#client-policy)). |
| a local `flags` list in `[session.clients.claude]` or `[session.clients.codex]` | A local list replaces the packaged one whole: add its agent-pm entry, Claude `"--settings", '{"enabledPlugins": {"agent-pm@agent-pm": false}}'`, Codex `"-c", "plugins.agent-pm@agent-pm.enabled=false"`, and for Codex the browser, computer use, Apps and `tool_suggest` entries of its packaged list ([Session settings](sessions.md#session-settings)). |
| permission flags in a local `flags` list: `--permission-mode`, `--dangerously-skip-permissions` (`[session.clients.claude]`, `[delegate.policy.claude]`), `-s`, `approval_policy`, `approvals_reviewer`, `--dangerously-bypass-approvals-and-sandbox` (`[session.clients.codex]`, `[delegate.policy.codex]`) | Remove them: permission flags live only in `[session.clients.<client>.modes]` `auto` and `yolo` ([Client policy](sessions.md#client-policy)); in `flags` they reach every Host, the Docker Host's yolo sessions too. Change a mode there (a local list replaces that mode whole), e.g. `[session.clients.codex.modes] auto = [...]`. Keep `--strict-mcp-config` in `[delegate.policy.claude]` and `"-c", "mcp_servers={}"` in `[delegate.policy.codex]`. |
| scripts or prompts passing `-- --permission-mode auto` to Claude workers | Drop it: auto mode adds it, and on the Docker Host it would sit beside yolo's. |
| Codex sessions started before a resume read the current `[session.clients.codex] flags` | Their recovery state also holds that list as it was at their start, which a resume repeats after the current one: an entry since dropped from a local list stays in force for them. Close and start them again. |
| `--add-dir` in a local `[session.clients.codex] flags` list | Remove it and grant the directory through the role's `write` dirs: left there, every Codex launch refuses with `--add-dir: [clients.codex] flags grant no directory`. |
| a local `[delegate.policy.codex] flags` list | Add `"-c", "mcp_servers={}"` to it: a local list replaces the packaged one whole, and without it a Codex role run loads the MCP servers your Codex config names ([Client policy](sessions.md#client-policy)). |
| Codex role runs started before `[policy.codex]` packaged `-c mcp_servers={}` | A resume keeps their old flags, and with them your MCP servers: close and start them again. |
| Codex sessions started before this upgrade | Their recovery state keeps the old `-s` and approval flags, which a resume adds to its mode's (on the Docker Host `--dangerously-bypass-approvals-and-sandbox` overrides them): close and start them again to drop them. |
| Claude sessions started before this upgrade | Their `client-resume` refuses with `bad resume state`: its state file lacks the launch's flags, Access, model, effort and name that a resume now replays ([Client policy](sessions.md#client-policy)). Close and start them again. |
