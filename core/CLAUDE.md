# core

The portable core pack: `src/compose.py` compiles `team/` text (`guide.md` opens the prompt; what goes where: the root `CLAUDE.md` › Roles, tasks, rules) and `output/` into a prompt; `src/drive.py` runs it through a client (`src/clients/`) and a runner. It knows nothing of Linear or a fixed docs repo (`docs/adr/0001`). It is the Claude Code plugin `agent-pm` (`.claude-plugin/plugin.json`; `version` changes only when the user says), skills in `skills/`. Only `core/` is installed, copied per version to `~/.claude/plugins/cache/agent-pm/agent-pm/<version>/`: a skill or script references nothing outside it, a skill naming core's files by `${CLAUDE_SKILL_DIR}/../../…`, the only variable its `allowed-tools` rules get.

## Commands

```bash
python3 core/src/drive.py --role R [--task T] --input TEXT --out O --workdir W [--runner tui …] --dry-run   # the agent run's argv, cwd and env; starts nothing
python3 core/src/drive.py --client skill --role R [--task T]   # the prompt /agent-pm:act-as follows
python3 core/src/tui_claude.py --help                          # host claude in tmux: start, send, read, show
python3 core/src/drive.py --list [--client C]                  # each role and task, with its source; C's destinations
```

## Rules

- `team/` and `output/` say what an agent run does and reports, client-neutrally; how a client starts a run and gets its outcome and progress back lives in that client's class.
- Roles, tasks and templates also come from team dirs (`config.toml`'s `team_dirs` comment), found by name through `compose.Team`.
- `## Tasks` in `team/roles/<role>.md`, right after its intro, is the only list of the role's tasks (its task index): the sentence `` Pick the task below that fits the input; unsure → `<task>` (`<tasks>/<task>.md`). `` naming the default (the only selection rule), then one line per task `` - `<task>` (`<tasks>/<task>.md`): what, a skill it uses as its slash command; when; light|heavy ``. `compose.index` parses them: a default not listed, a path other than `<tasks>/<task>.md` or no `team/tasks/<task>.md` → `ConfigError`; a run given no task picks from it (`team/guide.md`). A team dir adds index lines and task files too (`config.toml`'s `team_dirs` comment).
- A task marks where an agent run reports progress with a line `[agent-pm-progress:<name>] what to report`, under its own **Report progress** item (a step, or a bullet under the parent it belongs to), never inside another item; the client's `handover()` says how the run reports it.
- Run values are `compose.PARAMETERS` names (`<Workdir>`, `report`, …), each defined once in the prompt's `# Parameters` under the hard rule `compose.RULE`; `team/` and `output/` text use the names, never a `{{…}}` placeholder for one. `report` counts as used only as a code span starting with it (`` `report …` ``); a used name Parameters can't define raises `ConfigError`.
- A section reference in `team/` and `output/` text is a link: text the full path in the composed prompt, target that path's anchor (`[Engineer › Repo](#repo)`); a bold item links its section (`[Principles › Work › Worktree](#work)`); words after the path stay outside the link. A task or method file's section isn't in the prompt: plain `` `<tasks>/<task>.md` › Steps › Which build `` (`<task>`: every task in the role's index), `` `<methods>/ultracode.md` › Rules › Voting ``. `compose.render` writes an `<a id="…"></a>` line before a repeated heading, but the prompt's order varies with destination and templates: avoid repeating a heading. `compose.reference_errors` checks the references (`compose_test.py` on core's text, `drive.py` on a team dir's).
- `src/repo.py` is stdlib-only and imports nothing from `src/`. `repo.checkout` is the one checkout path rule, for any caller. Symlinks in a `repo.py worktree` checkout follow `config.toml`'s `trusted_dirs` comment, set in the worktree's own config (which turns on the clone's `extensions.worktreeConfig`); an existing worktree whose setting disagrees is refused: remove it, run again.
- Runners: `drive.RUNNERS` (`--runner`, default `headless`); `tui` hosts the client's `Launch.interactive` through `src/tui_claude.py`. A new runner is a `drive.Runner` naming its `Launch` field in `starts`.
- `src/tui_claude.py` stays one file usable alone: tmux and the stdlib, Python 3.9 syntax, importing no core module and reading no config (`tui_claude_test.py` checks). Its tmux, `sh`, `pgrep` and `osascript` calls go through the injectable `proc`, so unit tests run none. A live check uses a private server: `tmux -S <socket>` on every call, cleanup included (a program calling bare `tmux`: `env -u TMUX TMUX_TMPDIR=<dir>`); inside a tmux pane `$TMUX` beats `TMUX_TMPDIR`, so `TMUX_TMPDIR=… tmux kill-server` kills the caller's server.
- Every printed attach command is `tui_claude.attach_command`'s (it adds `$TUI_ATTACH_PREFIX`); no command it runs carries the prefix. `tui_claude.start`, `tui_claude.respawn` and `drive.py` drop `tui_claude.PARENT_KEYS` from their child's env (why: its comment).
- The built-in show (`open_pane`, when `show` is unset): an opener in tmux that a client shows gets a grid in its window (`tile`); else panes stack by opener (`opener()`); `--split`/`--split-from` split a chosen pane instead, outside the grid (a `show` command ignores both). What each does: `skills/tmux/SKILL.md` › Start 3. The only placement state stored: `@opener`, `@pane` (sessions), `@grid-manager`, `@grid-per-column`, `@grid-tiles`, `@grid-busy`, `@grid-panes` (grid window options), the grid's window hooks (per `grid_retile`) and its lock files beside the tmux socket, and `roster.json`'s `opener`, `pane`, `split`, `split_from` (`src/manager.py`, validated on read); every value is read back only after a fullmatch (`@grid-busy` is only compared with its window id): any same-user process can set them. A `show` command runs with `/bin/sh -c` in the driver's context: it carries the trust of `commands`.
- `drive.py --detach` (needs an events file: `--events`, else the manager directory's, `skills/tmux/SKILL.md` › Start 1) checks the run, then starts the same command as the driver in a new detached tmux session `<prefix>-<sid[:8]>-drive` (never a `TUI_SESSION`) on the caller's tmux server, with the run's opener (a tui run's, the caller's) as its `@opener` and no `@pane` (so the grid gives it no cell; `crew.py stop-all` finds it by `@opener`), records it in the roster when the events file is a manager directory's (`src/manager.py`), and exits. When the driver ends on its own or on one of `drive.SIGNALS` (`tmux kill-session` included), it appends one `outcome` line to the events file (`skills/tmux/SKILL.md` › Role runs).

## An agent run's command

The claude client's (`src/clients/claude.py`), as `drive.py … --dry-run` prints it; env `[clients.claude.env]`:

```bash
claude -p '<prompt>' --session-id <sid> --model <tier's> --effort <effort's> <[clients.claude] flags> --setting-sources user \
  --output-format stream-json --verbose --settings '{"enabledPlugins": {"agent-pm@agent-pm": false}}' \
  --add-dir <dir>… --allowedTools 'Bash(<command>)'…
```

- A resume: `--resume` for `--session-id`, in the session's recorded cwd with its settings. `--add-dir`: `team/tasks/` (or the task view: `config.toml`'s `team_dirs`), the `read`/`write` dirs, and the workdir when the cwd is another. A trusted cwd: `--setting-sources user,project,local` and, with a `.mcp.json`, `--mcp-config <cwd>/.mcp.json`.
- No deny list: `--allowedTools` pre-approves the role's `commands` and `report.py`; auto mode and the user's settings decide the rest.
- tui: `claude '<prompt>' …` without `-p`, `--output-format` and `--verbose`, plus `--name <session>` (`<prefix>-<sid[:8]>`, `--prefix` default `<role>`) and a `Stop` hook in `--settings`; its events file (Rules: `drive.py --detach`), if any, gets its `done|blocked|dead` lines. `drive.py` prints `tmux attach -t '=<session>'` and shows the session (Rules: the built-in show); no pane to split → only the attach command, with the reason. In a container: `skills/tmux/SKILL.md` › In a container, or a `show` command asking a host-side watcher to attach.
- tui give-up: after the nudge, `STOP_LIMIT` more turn ends without an outcome (a progress report resets the count), or `WAIT_LIMIT` after the last progress report or the start without one → `drive.py` prints the attach command, leaves the session and exits 1. Until then an unanswered dialog waits in the pane: interactive `claude` asks there to trust a new folder (`-p` doesn't) and, without auto mode (Haiku, tier 4), for what isn't pre-approved; a dialog opened within about a second of a turn end gets the nudge's keys. After the outcome or a give-up the session is an unwatched agent with the run's pre-approvals and `drive.py`'s environment, nothing it does reported: end it with `tmux kill-session -t '=<session>'` (in a manager's roster: `skills/tmux/SKILL.md` › Direct › Stop).
- `claude` needs (nothing checks; a missing one fails the run): `-p`, `stream-json`, `--resume`, `--permission-mode auto`, `CLAUDE_CODE_PRINT_BG_WAIT_CEILING_MS`; for tui, interactive mode and `Stop` hooks in `--settings`; subagents, web search and fetch, file and shell tools; the Workflow tool and built-in `/deep-research` (deep research).
- Tests that run `drive.py`, `crew.py` or `tui_claude.py` as a process put the repo's `tests/integration/core/fake_claude.py` on PATH as `claude` (its docstring: the scenario format). It rejects an option it doesn't know: a new option in this command goes into it too. Their tmux is a private server: `tests/integration/core/live_tmux.py`.

### Codex headless

Select Codex with `drive.py --client codex`. From the repository root, a fresh workdir run can be started with:

```bash
core="$(pwd)/core"
work="$(mktemp -d)"
(cd "$work" && python3 "$core/src/drive.py" --client codex --role dummy-tester --task echo \
  --input "Hello." --out "$work/out.md" --workdir "$work")
```

Add `--dry-run` to inspect the command without starting Codex. `[clients.codex.tiers]` and `[clients.codex.efforts]` in `config.toml` choose its model and reasoning effort; override a changed model in `~/.agent-pm/core.local.toml`. The client uses `codex exec --json -s workspace-write` with `approval_policy="on-request"` and `approvals_reviewer="auto_review"` config overrides. These also apply to resume and override operator defaults. Readable Codex events and stderr go to the driver, while only `report.py` progress and outcome entries count as reports. Its final reply does not count as an outcome. `--runner tui` is unavailable.

- **Recovery:** agent-pm's `--sid` is the run ID; Codex reports a separate native UUID in `thread.started`. Core saves the original effective Codex options under the operator's `~/.agent-pm/core-sessions/` before launch, then durably binds the first native UUID and mirrors it as `client_session` in `<workdir>/run.jsonl`. The run record is writable by the agent and never authorizes recovery. Resume with the same `--client codex --workdir <workdir> --sid <run-id> --resume`, plus role, task, input and out as usual. Core checks that saved effective paths remain covered by the recorded writable roots and keep the recovery store isolated. Core requires the saved mapping and matching Codex session file under the saved `CODEX_HOME`; a missing ID or file fails before Codex starts. The original cwd, project-setting decision, model, effort, directory grants and shell network setting remain in force even if the current config changes. Saved commands record audit intent; Codex continues to control command approvals through its own settings and review. The recovery store must be outside explicit writable grants and implicit temporary directories (`TMPDIR`, `/tmp`, `/private/tmp`, `/var/tmp`). Current role and task content still composes the new prompt; review config changes before resuming. A trusted cwd must remain in `trusted_dirs`. Previous progress and outcomes remain in the append-only run record.
- **Inspection:** `drive.session_info(client, workdir, run_id)` returns native ID, file existence, last file activity and a quoted interactive resume command when available. Its capability flags distinguish unsupported inspection from a session that has not reported an ID. The manual command uses the saved cwd, `CODEX_HOME` and access options. Usage is explicitly unsupported (`usage_supported=False`); no token count is inferred from the transcript.
- **Directories and commands:** every `--add-dir` grants read/write access, including entries listed under `read`; `-c sandbox_workspace_write.writable_roots=[]` drops any root Codex's own config adds, so `Launch.writable_roots` lists every root (the team dir guard: `config.toml`'s `team_dirs`). `commands` and `gate` express intent; they do not preapprove shell calls in Codex. Automatic review decides eligible approval requests, and an approved escalation may access files or the network beyond the sandbox. A denied command stays denied; the driver does not retry it outside the sandbox. Keep sensitive directories out of `read` as well as `write`.
- **Network:** `[clients.codex].shell_network = false` disables network for sandboxed shell commands by default; set it to `true` in the local config when the run needs shell network. This setting does not control web search, apps, or MCP, and approved escalations may exceed it.
- **Project settings:** an untrusted run must start inside its workdir. The client disables project AGENTS.md loading and rejects project-local `.codex` settings in its cwd ancestry or a project-controlled `CODEX_HOME`; use a clean workdir, or mark an operator-controlled cwd in `trusted_dirs` when its project settings are intended. Trusted runs may load those settings.
- **Portable resources:** prompts and access grants use absolute paths to the installed core's `src/`, `team/tasks/` (or the task view: `config.toml`'s `team_dirs`), and `team/methods/`. A Codex role run does not load the Claude plugin wrappers in `skills/` or need `${CLAUDE_SKILL_DIR}`. The repo's `tests/integration/core/fake_codex.py` gives process tests a fake CLI and an isolated HOME.

Install and authenticate the `codex` CLI and use Python 3.11+. A fresh run needs its own workdir and run ID.

## Add a client

1. **Module and config**: add `src/clients/<name>.py` and `[clients.<name>]` in `config.toml`. The name is a lowercase Python module identifier (`[a-z][a-z0-9_]*`); export a `Client` subclass, declare module `RUNS = YourClient.runs`, and set `implementation` to its class name (for example, `grok.py` exports `GrokClient`, and `[clients.grok]` declares `implementation = "GrokClient"`). `RUNS` exists because the class comes from config: before config loads, or when loading fails, a detached driver has no class to ask yet must still know whether it owns run events; `clients.definition` rejects a configured class whose `runs` disagrees. Unknown modules or missing declarations grant no authority. `clients.get(name, root)` imports that class from `clients.<name>` and removes `implementation` before passing the table to its constructor. The table is the registry; adding a client needs no shared code edit. The table is required even if the class sets `needs_config = False` (then its constructor receives `{}`). `Client.keys` declares client-specific config keys, including `"roles"` if it accepts per-role entries; run keys are allowed already.
2. **Launch** (`runs = True`): `launch()` maps `run.tier` and `run.effort` through its config (no mapping → `ConfigError`). Handle `access.dirs`, `access.commands`, `access.cwd` and `access.project` according to the client's actual capabilities (`docs/adr/0003`); document unsupported permissions rather than implying they are enforced. Fill `transcript`, `resume` and `interactive` only when the client supports those capabilities. A client with recoverable native sessions can provide an opaque JSON `Launch.session_state` and explicit `Launch.writable_roots`, validate its own saved payload, emit typed `Event("session", session_id=…)`, and implement `prepare_session()`, `record_session()`, `resume_location()` and `session_info()`. The driver calls the client to persist its initial state before spawn and its native ID before delivering later output; recovery storage belongs to the client. For Codex grants and limitations, see [Codex headless](#codex-headless).
3. **Outcome and progress** (`docs/adr/0006`): `handover()`, the Output › Return text, tells the run to report with `report` (the Parameters name of `compose.report_command`): `progress <name> <text>`, and `outcome …` as its last action; `drive.validate` is the only outcome check. For clients with `interactive`, have it run the report command plus `stop` at each turn end (claude: a `Stop` hook), plus `--pending KEY` when the hook's stdin JSON lists in-flight background work at top-level `KEY` (claude: `background_tasks`): tui nudges a run that stopped without an outcome, never one with pending work. Without `stop` lines tui never nudges; it gives up only after `WAIT_LIMIT`.
4. **Resolution**: `drive.plan` and `drive.inline` use `compose.resolve`; its docstring defines caller trust and layer precedence. Never set trust from issue text.
5. **Capabilities and tests**: put client-specific behavior in the discovered class, including `handover()`, `launch()` and `events()`. A capability it cannot provide should fail clearly or remain unavailable through the class interface, not through a shared client-name check. Test its argv, an unmapped tier and events from sample output in the repo's `tests/unit/core/drive_test.py`; test resume and `interactive` when supported, or a clear rejection when unavailable. `tests/integration/core/extension_client_integration_test.py` proves an additional client module plus config table reaches dry-run, handover, catalog and resolution without production dispatch edits.

Done when `drive.py --client <name> --dry-run` (and `--runner tui`, when it has `interactive`) prints the expected command for every role in `config.toml` and the suite passes.
